- 対象: `manifest.json` / `content.js` / `content.css` / `README.md`
- 前提として読んだもの: `ideas/20261008-aws-region-checker.md`(仕様)、`docs/20261008-implementation.md`(実装説明)
- 方法: 静的な読解のみ。実ブラウザ・実コンソールでは動かしていない。実 DOM に依存する指摘は「推測」と明記した。

## 結論

- 高 1 件、中 4 件、低 10 件。
- 最大の問題は、仕様の中核「リージョンが変わったら再表示」が、リージョンを一巡した後は成立しないこと(指摘 1)。実装説明に既知の制約として書かれているが、権限を増やさずに直せる見込みがある。
- セキュリティ(外部通信なし・textContent のみ・権限なし・認証情報を読まない)は仕様どおりで問題なし。
- 実 DOM の前提(リージョンボタンのセレクタ・文言・親要素のレイアウト)は実装説明のとおり未検証のまま。指摘 2・4 はそこが外れたときに黙って機能しなくなる経路。

## 仕様への適合

### 1. [高] 一度確認したリージョンに同じタブで戻ると再表示されない

- 場所: `content.js:48-63`(`getConfirmed` / `setConfirmed`)、`content.js:114`
- 再現シナリオ:
  1. 東京(`ap-northeast-1.console.aws.amazon.com`)で `ap-northeast-1` を入力 → 消える
  2. `us-east-1` に切替 → 表示される → `us-east-1` を入力 → 消える
  3. 同じタブで東京に戻る → **表示されない**
  4. 再び `us-east-1` へ → **表示されない**
  - 以後そのタブでは、確認済みの 2 リージョン間をいくら往復してもバナーが出ない。
- 根拠: `sessionStorage` はオリジン単位。コンソールはリージョンごとにホスト名が変わるので、各オリジンに「自分のリージョンを確認済み」が残り続ける。保存値を 1 件にしている意図(リージョンが変わったら前の確認を無効にする)が、オリジンをまたぐと働かない。
- 仕様との差: 仕様 13 行目「リージョンが変わったら再表示」。仕様の例(14 行目)は 2 ステップ目までなので通るが、3 ステップ目以降で崩れる。リージョンを行き来する作業こそ取り違えが起きる場面なので、中核機能の欠落と判断した。
- 同一オリジン内との不整合: `us-east-1` の EC2 と IAM(`Global`)は同じオリジンなので、往復するたびに毎回再表示される。オリジンをまたぐ切替だけ再表示されず、挙動が揃っていない(実装説明 57 行目に記載済み)。
- 修正案(権限を増やさない): ページ読み込み時に `document.referrer` のホスト名から `findRegion` でリージョンを取り、現在のリージョンと違えば保存値を消す。リージョン切替はオリジンをまたぐ全画面遷移で、既定のリファラポリシーでもオリジン(=リージョンを含むホスト名)は渡る。数行で済む。
  - この案は推測を含む。切替時にリファラが残るか(サインイン系ドメインを経由しないか、コンソールが `no-referrer` を指定していないか)は実コンソールで要確認。
  - リファラが使えない場合は、`storage` 権限で `chrome.storage.session` を使うしかなく、仕様の「permissions なし」を見直す判断になる。`storage` はインストール時の警告を出さない権限だが、タブ単位の管理には別途工夫が要る。

### 5. [中] README が指摘 1 の制約に触れていない

- 場所: `README.md:11-12`, `README.md:16`
- 内容: 「リージョンが変わると再表示します」「確認済みの状態はタブごとの `sessionStorage` に保存され、タブを閉じると消えます」とだけ書かれている。指摘 1 の「戻ったときは出ない」は実装説明にしかない。
- 再現シナリオ: README を読んだ利用者が、東京 → us-east-1 → 東京と戻ったときにバナーが出ないのを見て「東京は確認済みだから安全」ではなく「拡張が壊れた」あるいは「出ないのだからリージョンは変わっていない」と受け取る。
- 修正案: 指摘 1 を直すなら不要。直さないなら「制限」節に 1 行足す。

### 仕様適合で問題なしの項目

- 構成(3 ファイル、ビルドなし、Shadow DOM 内にスタイルを閉じる): 問題なし。
- `matches` が `https://*.console.aws.amazon.com/*`、`permissions` / `host_permissions` なし: 問題なし。`web_accessible_resources` は権限ではなく、`matches` も同じホストに限定されている。
- リージョン取得の順序: グローバル判定をホスト名より前に置いたのは仕様の順(ホスト名 → クエリ → ボタン)からの逸脱だが、IAM が `us-east-1` と表示されるのを避けるためで、実装説明に理由がある。妥当。
- 「全リージョンで表示」: 正規表現 `^[a-z]{2}(-[a-z]+)+-\d+$` は `ap-northeast-1` `mx-central-1` `il-central-1` `us-gov-west-1` 形式を通す。問題なし。
- `browser_specific_settings.gecko.id` あり: 問題なし。
- 名称・非公式の明記・AWS ロゴ不使用: 問題なし。

## 正しさ(バグ・エッジケース)

### 2. [中・推測] ボタンが非表示でもその隣に挿入し、fixed に落ちない

- 場所: `content.js:98-110`
- 再現シナリオ: ウィンドウ幅が狭く、ナビがリージョンボタンを折りたたむ(`display: none` の要素として DOM には残す、またはデスクトップ用とモバイル用の 2 つを持つ)状態。`document.querySelector(REGION_BUTTON)` は要素を返すので `button.before(host)` が実行され、バナーは非表示のコンテナの中に入る。`button` が truthy なので `data-fallback` も付かない。結果、バナーが画面に出ないまま、エラーも出ない。
- 根拠: `place()` は要素の有無しか見ておらず、見えているかを確認していない。実際のナビが狭い幅でどう振る舞うかは未確認なので推測。
- 関連(推測): バナーは `white-space: nowrap` で幅がおよそ 400px ある(ラベル + `14em` の入力欄)。表示されていても、ナビの他の項目を押し出すか、親が `overflow: hidden` なら切れる。
- 修正案: `button.getClientRects().length === 0` なら `button` を無いものとして扱い、fixed フォールバックに回す。1 行で足りる。

### 3. [中] キーイベントの伝播停止が capture 側のハンドラに効かない

- 場所: `content.js:89-92`
- 内容: `stopPropagation()` を入力欄自身のバブル段階で呼んでいる。ページ側が `document` や `window` に capture で登録したハンドラは、それより先に実行される。
- さらに、Shadow Root が `closed` なので、ページ側から見た `event.target` は入力欄ではなくホストの `<div>` になる。「入力欄にフォーカス中はショートカットを無視する」というページ側の判定が効かない。
- 再現シナリオ(影響部分は推測): コンソールが単一キーのショートカットを capture で拾っているサービスの画面で、バナーに `us-east-1` と打つ。`s` や `/` でショートカットが発火し、検索欄にフォーカスが移る、またはパネルが開く。
- 根拠: DOM イベントの伝播順(capture → target → bubble)と Shadow DOM のリターゲットは仕様上の挙動で確定。AWS コンソールに該当するショートカットがあるかは未確認。
- 修正案: 実コンソールで問題が出るかを先に確認する。出るなら、コンテンツスクリプト側で `window` に capture でリスナーを登録し、`event.composedPath()[0] === input` のときだけ `stopPropagation()` する(コンテンツスクリプトの `composedPath()` は closed な自前の Shadow Root の中まで見える想定だが、これも要確認)。出ないなら現状のままでよい。

### 4. [中・推測] ボタン文言への依存が弱い

- 場所: `content.js:17`(`GLOBAL_LABELS`)、`content.js:37-39`、`content.js:44`
- (a) 言語: `GLOBAL_LABELS` は `global` と `グローバル` だけ。コンソールの表示言語が韓国語・中国語・フランス語などの場合、パス一覧にないグローバルサービス(例: `us-east-1.console.aws.amazon.com/wafv2/...?region=global`、サポートセンター)でボタンが一致せず、ホスト名から `us-east-1` と表示される。グローバルなサービスを `us-east-1` と表示するのは誤表示。
- (b) 完全一致: `textContent.trim().toLowerCase()` の完全一致なので、ボタン内にスクリーンリーダー用の隠しテキストやアイコンの `<title>` が含まれると一致しない。
- (c) 順 3: 実際のリージョンボタンはリージョン名(「東京」「Tokyo」など)だけを表示し、コード(`ap-northeast-1`)はメニューを開いた一覧側にしか出ない可能性が高い。その場合 `content.js:44` は常に `null` を返す。ホスト名にもクエリにもリージョンがないページでは、バナーが出ないまま何も知らされない。
- 根拠: いずれも実 DOM を見ていないので推測。実装説明の「未確認の前提」にも挙がっている。
- 修正案: 実コンソールでボタンの `textContent` を、リージョナルなページとグローバルなページの両方で確認する。(a) はクエリ `region=global` を `Global` 扱いに加えると、言語に依存しない判定が 1 つ増える。(c) が外れているなら順 3 のコードは消す(YAGNI)。

### 6. [低] 挿入回数の上限がリセットされない

- 場所: `content.js:20`, `content.js:27`, `content.js:100-104`
- 再現シナリオ: コンソールを 1 つのタブで長時間使う。SPA 内の画面遷移のたびにナビが再描画されてバナーが外れ、再挿入で `navInserts` が 1 増える。確認 → リージョン変更(同一オリジン内の Global ↔ us-east-1)による出し直しでも 1 増える。累計 20 回に達すると、それ以降はボタンがあっても fixed 表示に固定され、ページを再読み込みするまで戻らない。
- 根拠: `navInserts` は増えるだけで、減る・戻す箇所がない。「無限ループの打ち切り」が目的なのに、正常な再描画も数えている。
- 修正案: 回数ではなく頻度で判定する。前回の挿入から数秒以上空いていたらカウンタを 0 に戻す。

### 7. [低] `createBanner()` が途中で失敗すると半端な状態が残る

- 場所: `content.js:65-96`, `content.js:119`
- 再現シナリオ(Chrome): コンソールのタブを開いたまま拡張を更新または再読み込みする。古いコンテンツスクリプトは残り、`chrome.runtime` が無効になる。その時点でバナー未作成(確認済みで非表示)だった場合、次にリージョンが変わると `createBanner()` が 66 行目で `host` を代入した後、71 行目の `chrome.runtime.getURL` で例外を出す。`host` は非 null、`label` と `input` は null のまま残る。以後 `update()` は `if (!host)` を素通りして 122 行目の `label.textContent` で `TypeError` を出し続ける。DOM が変化するたびに 200ms 間隔でコンソールにエラーが出て、バナーは出ない。
- 根拠: モジュール変数 `host` を、構築が終わる前に代入している。
- 影響: 更新直後の既存タブに限られ、ページ再読み込みで直る。新しいスクリプトは既存タブに注入されないので、その間バナーが出ない。
- 修正案: ローカル変数で組み立て、最後に `host` / `label` / `input` へ代入する。`getURL` を先頭に移すだけでも足りる。

### 8. [低] `setItem` だけ失敗するとバナーを消せない

- 場所: `content.js:48-63`
- 再現シナリオ: `sessionStorage` の容量がページ側のデータで埋まっていて、`getItem` は成功し `setItem` だけ `QuotaExceededError` を出す状態。正しいリージョンを入力すると `setConfirmed` は `confirmedFallback` にだけ保存する。直後の `update()` で `getConfirmed()` は `getItem` が成功するので `null`(または古い値)を返し、`confirmedFallback` は見られない。バナーは残り、入力欄には正しい値が入ったまま何も起きない。
- 根拠: フォールバックを読むのが `getItem` が例外を出したときだけになっている。
- 修正案: `setItem` が失敗したらフラグを立て、以後は `confirmedFallback` を使う。

### 9. [低・推測] ナビ描画前の一時的な誤表示

- 場所: `content.js:34-46`
- 再現シナリオ: パス一覧にないグローバルサービス(ホスト名は `us-east-1`)を開く。`document_idle` の時点でナビがまだ描画されていないと、`getRegion()` はホスト名から `us-east-1` を返し、右上 fixed に「現在のリージョン: us-east-1」が出る。ナビが描画されると `Global` に変わり、入力欄もクリアされる。その間に `us-east-1` と打ち切ると、グローバルなページで `us-east-1` を確認済みにできる。
- 根拠: ナビが遅延描画されることは仕様 37 行目の前提。実際の時間差は未確認。
- 修正案: 対応不要の可能性が高い。指摘 4 (a) のクエリ判定を足すと、該当ページの一部は最初から `Global` になる。

### 10. [低・推測] bfcache から復元されたとき再評価しない

- 場所: `content.js:142-144`
- 再現シナリオ: `us-east-1` の EC2 で確認済み(非表示)→ IAM へ全画面遷移して `Global` を確認 → ブラウザの「戻る」で EC2 が bfcache から復元される。保存値は `Global` なので本来は `us-east-1` で再表示されるはずだが、スクリプトは再実行されず、`popstate` も来ないので、次に DOM が変化するまでバナーが出ない。
- 根拠: コンソールのページが bfcache の対象になるかは未確認。SPA は DOM 変化が頻繁なので、実際の遅れは短いと見込まれる。
- 修正案: `pageshow` を `popstate` と同じ並びに 1 行足す。

### 11. [低] CSS 関連

- 場所: `content.css:3-17`, `content.js:69-71`
- (a) 確定(発生条件は推測): CSS が読めなかった場合、`position: fixed` も効かない。フォールバック時はホストが `document.body` の末尾に通常フローで入るので、ページ最下部に出るか、コンソールのレイアウト次第で見えない。実装説明 138 行目の「無装飾で表示される(機能は動く)」は、ナビ挿入時にしか当てはまらない。
  - 修正案: `position` / `top` / `right` / `z-index` だけは JS から `host.style` に直接設定する。
- (b) 確定: `:host` の宣言は、ページ側の CSS がホスト要素に当たった場合に負ける(外側のスタイルが `:host` より優先)。`all: initial` が切るのは継承であって、`header div { ... }` のようなページ側セレクタは防げない。実害があるかは実 DOM 次第。
- (c) `<link>` の読み込み完了まで一瞬スタイルなしで表示される(実装説明に記載済み)。対応不要。

### 12. [低] 全角入力では一致しない

- 場所: `content.js:85`
- 再現シナリオ: IME がオンのまま `ａｐ－ｎｏｒｔｈｅａｓｔ－１` と全角で確定する。`trim().toLowerCase()` では半角と一致せず、バナーが消えない。理由も表示されない。
- 修正案: 比較前に `normalize("NFKC")` を挟む。日本語利用者向けの拡張なので費用対効果はある。

### 正しさで問題なしの項目

- `MutationObserver` の自己ループ: 自分の挿入で 1 回だけ余分に `update()` が走るが、2 回目は DOM を変えないので止まる。Shadow Root 内の変更と属性の変更は監視対象外。問題なし。
- 負荷: DOM 変化を 200ms にまとめ、1 回あたり `querySelector` 2 回と `sessionStorage` 読み取り 1 回。問題なし。
- `shownRegion` が null のまま `toLowerCase()` に届く経路: バナーが外れている間は `input` イベントが来ないので到達しない。問題なし。
- マルチセッション形式のホスト名(アカウント ID を含むラベル): 正規表現に一致するラベルだけを取るので問題なし。
- フレーム: `all_frames` 未指定でトップフレームのみ。重複表示なし。問題なし。
- 途中入力・大文字入力・貼り付け(`input` イベントで拾える): 問題なし。

## Chrome / Firefox 両対応

### 13. [低] manifest の細部

- 場所: `manifest.json:18-26`
- (a) Chrome は `browser_specific_settings` を認識せず、`chrome://extensions` に「Unrecognized manifest key」の警告を出す。動作に影響なし。README に一言あると、読み込んだ人が不具合と誤解しない。
- (b) `data_collection_permissions` を解釈するのは Firefox 140 以降。`strict_min_version` の 127〜139 では未知キーとして無視される見込みで、動作には影響しない(推測。AMO の検証で警告になるかは提出時に確認)。
- (c) アイコンがない。ストア提出時に必要(実装説明に記載済み)。

### 両対応で問題なしの項目

- `chrome.runtime.getURL`: Firefox も `chrome` 名前空間を提供する。問題なし。
- MV3 形式の `web_accessible_resources`(`resources` + `matches`): Chrome・Firefox とも対応。問題なし。
