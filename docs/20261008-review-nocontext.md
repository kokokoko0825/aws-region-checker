# コードレビュー(コンテキストなし): aws-region-checker

- 対象: `manifest.json` / `content.js` / `content.css` のみ(ideas/, docs/, README.md, git ログは未読)
- 方法: 静的読解のみ。実ブラウザ・実 AWS コンソールでの動作確認はしていない。AWS コンソールの DOM や URL 体系に依存する指摘は「推測」と明記した。
- コードから読み取った仕様: AWS コンソールで現在のリージョンをバナー表示し、ユーザーがリージョンコードを入力するまで消さない。確認済みリージョンは `sessionStorage` に 1 件だけ保持する。

## 総評

重大度「高」の指摘はない。XSS・権限過剰・外部通信といったセキュリティ上の問題は見当たらない。
主な懸念は「確認済み」状態の持ち方(指摘 1, 2, 3)と、リージョンを判定できないときに黙って何も出さない点(指摘 4)。どちらも「誤リージョン操作を防ぐ」という目的に対して、警告が出ない方向・消せない方向に倒れるケースがある。

## 正しさ(バグ・エッジケース)

### 1. 確認済み状態がオリジン単位で残り、リージョンを戻したときに再確認されない — 重大度: 中

- 該当: `content.js:18`, `content.js:48-63`, `content.js:114`
- 再現シナリオ:
  1. 同一タブで `us-east-1.console.aws.amazon.com` を開き `us-east-1` と入力 → このオリジンの `sessionStorage` に `us-east-1` が保存される。
  2. リージョンを東京に切り替え(`ap-northeast-1.console.aws.amazon.com` へ遷移)、`ap-northeast-1` と入力 → 別オリジンの `sessionStorage` に保存される。
  3. バージニアに戻す → `us-east-1` オリジンの `sessionStorage` には手順 1 の値が残っているため `region === getConfirmed()` が真になり、**バナーが出ない**。
- 根拠: `sessionStorage` はオリジン(ホスト名)ごとに分離される。AWS コンソールはホスト名にリージョンを含むので、キー 1 件の「直近に確認したリージョン」という設計が、実際には「このタブで一度でも確認したリージョン全部」として振る舞う。一方、ホスト名が変わらない場合(指摘 2 の Global ⇄ リージョナル)は 1 件上書きになり、挙動が一貫しない。
- 同じ原因の派生:
  - タブ内でアカウントやロールを切り替えても(本番 ⇄ 開発)確認済みのままになる。
  - ブラウザのセッション復元やタブ複製で `sessionStorage` が引き継がれると、翌日でもバナーが出ない(推測: ブラウザ設定に依存)。
- 修正案: どちらの仕様が意図かを決めて揃える。
  - 「リージョンが変わるたびに再確認」が意図なら、ページ自身の `sessionStorage` ではなく拡張側の領域(`chrome.storage.session` をタブ ID 単位で使う等)に「直近確認リージョン」を持つ。`storage` 権限と background が必要になるので、KISS を優先するなら次の案。
  - 「タブ内で一度確認したリージョンは再確認しない」が意図なら現状の挙動で足りるので、指摘 2 を直して一貫させる。

### 2. 確認済みが 1 件だけなので Global とリージョナルを行き来するたびに再入力になる — 重大度: 中

- 該当: `content.js:35`, `content.js:56-63`, `content.js:114`
- 再現シナリオ: `us-east-1.console.aws.amazon.com/ec2/...` で `us-east-1` を確認 → 同ホストの `/iam/home` へ移動 → `getRegion()` が `Global` を返し、保存値 `us-east-1` と不一致でバナー表示 → `global` と入力すると保存値が `Global` に上書き → EC2 に戻ると `us-east-1` を再入力させられる。IAM と EC2 を往復するたびに繰り返す。
- 根拠: `setConfirmed` は単一キーを上書きする。IAM などは `us-east-1` ホストで配信されるため同一オリジンで値を取り合う(ホスト名は推測だが、コード内コメント `content.js:7` も同じ前提)。
- 修正案: 確認済みを集合(例: カンマ区切りや JSON 配列)で持つ。または Global のときはバナーを出すだけで入力を求めない。

### 3. `setItem` だけ失敗するとバナーを永久に消せない — 重大度: 中(発生頻度は低い)

- 該当: `content.js:48-63`
- 再現シナリオ: `sessionStorage` が容量上限に達している状態(`getItem` は成功、`setItem` は `QuotaExceededError`)で正しいリージョンを入力 → `setConfirmed` は例外を握りつぶして `confirmedFallback` にだけ保存 → 直後の `update()` で `getConfirmed()` は例外が出ないので `sessionStorage` の値(`null` または古い値)を返す → 不一致のままバナーが残り、何度入力しても消えない。
- 根拠: 読み取り側は「`getItem` が例外を投げたときだけ」フォールバックを使うが、書き込み側は「`setItem` が例外を投げたとき」にフォールバックへ頼る。失敗条件が読み書きで対称になっていない。
- 修正案: メモリ上の値を正とし、`sessionStorage` はリロード越しの復元用にだけ使う。例: `getConfirmed` を「`confirmedFallback` があればそれを返し、なければ `sessionStorage` を読む」にする。

### 4. リージョンを判定できないとき無言でバナーを出さない — 重大度: 中

- 該当: `content.js:41-45`, `content.js:113-118`
- 再現シナリオ: ホスト名にリージョンを含まず(`console.aws.amazon.com` や `s3.console.aws.amazon.com` など)、クエリに `region=` がなく、ボタン文言にもリージョンコードが含まれないページ → `getRegion()` が `null` → `host?.remove()` で非表示。ユーザーからは「確認済みだから出ていない」のか「判定できていない」のか区別できない。
- 根拠: `!region` と `region === getConfirmed()` を同じ分岐で扱っている。安全装置としては判定不能時に黙るのは危険側。該当するページが実在するかは推測(指摘 8 も参照)。
- 補足: リージョンがハッシュ側(`#/...?region=xx`)にあるページは `location.search` では拾えない(推測: そういう URL のサービスがあるかは未確認)。
- 修正案: ナビのリージョンボタンは存在するのにリージョンを判定できない場合は「リージョン不明」と表示する。少なくとも分岐を分けておく。

### 5. `navInserts` がリセットされず、長時間使うと恒久的に fixed 表示へ落ちる — 重大度: 中

- 該当: `content.js:20`, `content.js:27`, `content.js:98-110`
- 再現シナリオ: 1 つのドキュメントを開いたまま SPA 内で操作を続ける。ナビの再描画や、確認 → リージョン変化による再表示のたびに `navInserts` が増える。累計 20 回に達すると `button` を常に `null` 扱いにし、以後はリロードするまで右上 fixed 表示になる。
- 根拠: カウンタは「消され続けた場合」(コメント `content.js:19`)の暴走防止が目的だが、時間窓がなく累計で数えている。正常な再挿入と暴走を区別できない。20 回に達する頻度は実コンソールの再描画頻度次第(推測)。
- 修正案: 「直近 N 秒間の挿入回数」で判定するか、挿入後しばらく安定していたらカウンタを 0 に戻す。

### 6. バナー移動時にフォーカスが外れ、続きのキー入力がコンソールに流れる — 重大度: 低

- 該当: `content.js:98-110`
- 再現シナリオ: ページ読み込み直後、ナビ描画前に fixed 表示のバナーへ入力を始める → ナビが描画され `button.before(host)` でバナーがナビ内へ移動 → DOM 移動で `input` のフォーカスが外れる → 残りのキー入力(例: `us-east-1` の途中の文字)がページ本体に届き、コンソールのキーボードショートカットとして解釈され得る。ナビが再描画されて再挿入される場合も同じ。
- 根拠: フォーカス中の要素を DOM ツリー上で移動するとフォーカスは失われる(入力値は残る)。`content.js:89-92` でショートカット誤発火を避けているのに、この経路では防げない。
- 修正案: 移動前に入力欄がフォーカス中かを記録し、移動後に `input.focus()` を呼ぶ。closed な shadow root の参照を保持して `root.activeElement === input` で判定できる。

### 7. `createBanner` が途中で例外を出すと半初期化状態になる — 重大度: 低

- 該当: `content.js:65-96`, `content.js:119-123`
- 再現シナリオ: タブを開いたまま拡張を更新・再読み込みし、その後に初めてバナーを生成する場面(それまで確認済みで非表示だった等)→ `content.js:71` の `chrome.runtime.getURL` が "Extension context invalidated" で例外(推測: Chrome の挙動) → `host` は代入済みだが `label` / `input` は `null` のまま → 次回以降 `if (!host)` を通過せず `label.textContent` で `TypeError` が約 200ms ごとに出続ける。
- 根拠: モジュール変数 `host` への代入が関数の先頭にあり、構築完了前に「生成済み」と判定される状態になる。
- 修正案: ローカル変数で組み立て、最後にまとめてモジュール変数へ代入する。指摘 11 の対応で `getURL` 自体をなくせば、この経路は消える。

### 8. ボタン文言からのリージョン抽出は実質機能しない可能性 — 重大度: 低(推測)

- 該当: `content.js:37-38`, `content.js:44`
- 再現シナリオ: リージョンボタンの表示が「東京」「N. Virginia」のような表示名だけの場合、`buttonText.split(/[^a-z0-9-]+/)` の結果に `REGION_RE` に合うトークンがなく、常に `null`。
- 根拠: 第 3 候補はボタン文言にリージョンコード(`ap-northeast-1`)が含まれることを前提にしている。実 DOM は未確認なので推測。含まれないなら死んだコードで、指摘 4 の fail-open に直結する。
- 修正案: 実 DOM で文言を確認する。コードが含まれないなら削除する(YAGNI)か、コードを持つ別の属性・要素から取る。

### 9. Global 判定が日英 2 言語とハードコード一覧に依存 — 重大度: 低

- 該当: `content.js:8-17`, `content.js:35-39`
- 再現シナリオ: コンソールの表示言語が日本語・英語以外で、`GLOBAL_SERVICES` に載っていないグローバルサービスを開く → ボタン文言が `GLOBAL_LABELS` に一致せず、ホスト名の `us-east-1` をリージョンとして表示する。
- 根拠: `GLOBAL_LABELS` は `global` と `グローバル` のみ。`GLOBAL_SERVICES` は 7 件固定で、AWS 側のパス変更やサービス追加に追随できない(一覧の過不足は未検証)。
- 補足: バナー文言自体が日本語固定なので、対象ユーザーを日本語・英語に限る前提なら許容範囲。その場合も一覧の保守コストは残る。

### 10. `REGION_RE` と `matches` の対応範囲が不整合 — 重大度: 低

- 該当: `content.js:5`, `manifest.json:8`
- 内容:
  - `REGION_RE` は `us-gov-west-1` や `cn-north-1` に合う形だが、`matches` は `*.console.aws.amazon.com` だけなので GovCloud や中国リージョンのコンソール(別ドメイン)では動かない。対応外なら正規表現の `(-[a-z]+)+` は過剰、対応するなら `matches` が不足。
  - 先頭を `[a-z]{2}` に固定しているため、`eusc-de-east-1` のような 4 文字プレフィックスのリージョンには合わない(このリージョンのコンソールも別ドメインと思われるので現状は実害なし。推測)。
- 修正案: 対応パーティションを決め、正規表現と `matches` を揃える。

### 問題なしと判断した点

- 自分の DOM 挿入が `MutationObserver` を再発火させるが、2 回目の `place()` は `host.nextSibling === button` で何もしないので収束する。無限ループにはならない。
- `scheduleUpdate` は 200ms に 1 回へ間引かれ、`update()` の中身は `querySelector` 2 回程度なので、DOM 変化の多いページでも負荷は小さい。
- `pushState` を直接フックしていないが、SPA 遷移は DOM 変化を伴うので `MutationObserver` で拾える。
- `content.js:85` の `shownRegion.toLowerCase()` は、`shownRegion` が `null` になるのがバナーを DOM から外した後だけなので、ユーザー操作では `null` 参照にならない。

## ブラウザ拡張としての作法

### 11. `web_accessible_resources` で CSS を公開する必要がない — 重大度: 低

- 該当: `manifest.json:12-17`, `content.js:69-71`
- 内容: `content.css` をページから取得可能にしている。公開先は AWS コンソールに限定されているので影響は小さいが、次の点がある。
  - Firefox では `moz-extension://<インストールごとの UUID>/content.css` になり、ページ側は `performance.getEntriesByType("resource")` でこの URL を観測できる。closed shadow root の中に `<link>` を置いても隠せない。ブラウザ固有の識別子がページに見える。
  - Chrome では拡張 ID 固定の URL になり、拡張の導入有無をページが判別できる。
- 修正案: CSS を `content.js` 内の文字列にして shadow root に `<style>` で入れる(または `adoptedStyleSheets`)。`web_accessible_resources` と `chrome.runtime.getURL` が不要になり、指摘 7 と 12 も同時に解消する。ファイルも 1 つ減る。

### 12. CSS が読めなかった場合、フォールバック表示が実質見えなくなる — 重大度: 低(推測)

- 該当: `content.js:69-71`, `content.js:106-109`, `content.css:11-17`
- 再現シナリオ: `<link>` の読み込みがページの CSP 等で拒否される、または読み込み完了前 → `:host([data-fallback])` の `position: fixed` が効かず、`document.body` 末尾に無スタイルで置かれる。コンソールのレイアウト上、画面外や他要素の下になり見えない。
- 根拠: 表示位置を外部 CSS に全面依存している。Chrome は拡張リソースをページ CSP の対象外にするが、Firefox での扱いは未確認(推測)。読み込み完了までの一瞬は確実に無スタイルになる。
- 修正案: 指摘 11 のインライン化で解消する。

### 13. `:host` のスタイルはページ側 CSS に上書きされ得る — 重大度: 低(推測)

- 該当: `content.css:3-17`
- 再現シナリオ: コンソール側に `nav div { display: none }` や `header > * { margin: ... }` のようなセレクタがあり、ホスト要素(ただの `div`)に当たる → 通常宣言同士では外側ドキュメントの規則が `:host` より優先されるので、`display` や `position` が上書きされる。
- 根拠: `all: initial` を含め、`:host` 内の通常宣言は外側の通常宣言に負ける。実際に当たるセレクタがあるかは未確認。
- 修正案: 表示に必須の宣言(`display`, `position`, `top`, `right`, `z-index`)に `!important` を付ける。shadow 側の `!important` は外側の通常宣言に勝つ。

### 14. `stopPropagation` はキャプチャ段階のショートカットを止められない — 重大度: 低(推測)

- 該当: `content.js:89-92`
- 再現シナリオ: コンソール側が `document` / `window` にキャプチャ段階(`{ capture: true }`)でキー操作のリスナーを登録している場合、イベントは入力欄へ届く前にそのリスナーを通るので、入力中でもショートカットが発火する。
- 根拠: 対象要素でのバブリング段階の `stopPropagation` は、それ以前のキャプチャ段階には効かない。コンソールがどちらで登録しているかは未確認。
- 修正案: 実機で入力中にショートカットが発火しないか確認する。発火しなければ対応不要。

### その他(manifest)

- 権限: `permissions` / `host_permissions` なし。content script の `matches` だけで最小権限になっている。問題なし。
- `all_frames` 未指定(トップフレームのみ)、`run_at` 未指定(`document_idle`)。用途に合っており問題なし。
- `icons` が未定義。拡張管理画面やストア掲載で既定アイコンになる。重大度: 低。
- `description` は英語、UI 文言は日本語固定(`content.js:79`, `content.js:122`)。`_locales` もない。対象ユーザーを日本語話者に限るなら問題なし。
- `browser_specific_settings.gecko` の `data_collection_permissions` は新しい Firefox でのみ解釈され、`strict_min_version: 127.0` の範囲では無視されるだけなので問題なし。

## セキュリティ

問題なし(指摘 11 の識別子露出を除く)。

- DOM への出力は `textContent` のみで、`innerHTML` 等は使っていない。表示する値も正規表現で検証済みの文字列か定数。
- 外部通信なし。拡張 API は `chrome.runtime.getURL` だけ。
- `sessionStorage` に保存するのはリージョンコードだけで、秘匿情報は含まない。ただしページ側スクリプトから読み書きできる領域なので、ページが値を書き換えればバナーを消せる。AWS コンソール自身を信頼する前提なら問題なし。
- closed shadow root はセキュリティ境界ではないが、ここでは境界として使っていないので問題なし。

## アクセシビリティ / UX

### 15. 細かい点 — 重大度: 低

- 確認成功時に `host.remove()` でフォーカス中の入力欄ごと消えるので、フォーカスが `body` に落ちる。スクリーンリーダー利用者には何が起きたか伝わらない(`content.js:86-87`, `content.js:115`)。
- バナーに `role="status"` 等がなく、リージョンが変わってバナーが出ても読み上げられない(`content.js:73-76`)。
- Global のとき、プレースホルダは「消すにはリージョンを入力」のままで、`global` と打てばよいことが分からない(`content.js:79`, `content.js:122`)。
- IME オンで全角入力(`us-east-1`)すると一致しない(`content.js:85`)。比較前に `normalize("NFKC")` を通すと吸収できる。
- 貼り付けでも確認が通る。「手で打たせる」ことが目的なら抜け道になる(設計意図次第)。
- fixed 表示の `top: 56px`(`content.css:13`)はナビの高さを決め打ちしている。ナビの高さが変わると重なる。ナビ内表示では `white-space: nowrap` と入力欄 `14em` で横幅を取るので、狭いウィンドウでナビの他要素を押し出す可能性がある(推測)。
